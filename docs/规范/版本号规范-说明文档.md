# 版本号规范说明文档

> 移植自 IntelliJ 原版仓 `docs/发行说明/版本号规范-说明文档.md`，规则一致，落点按本仓事实改写。
> 两边机制为什么能统一，见 `docs/开发计划/20261128-2339-版本号规范对齐原版日期制-开发计划.md` §1。

## 版本号

1. **版本号位置**：`plugin.toml` 顶部的 `version`。它是 `.oiplugin` 的权威来源，`openidea-plugin pack` 直接读它。
   `Cargo.toml` 的 `package.version` 必须与之**逐字一致**（`scripts/check-version-format.sh` 是这个一致性的门禁）。
2. **命名格式**：`{年份}.{月份}.{日号}`
   - 年份：`YYYY`（如 `2026`）。
   - 月份：`M`，不补前导零（`2026.8.13`，不是 `2026.08.13`）。
   - 日号：`D`，不补前导零（`2026.11.5`，不是 `2026.11.05`）。
   - 示例：`2026.11.28`、`2026.12.1`、`2027.1.9`。
3. **发布规则**：一日一版
   - 一天最多一个版本号，版本号即发布当天日期。
   - 同日需再发（热修）并入次日：`2026.11.28` 当天发现缺陷，次日以 `2026.11.29` 发布。
   - 禁止同日递增后缀（`2026.11.28.1`）——四段不是合法 SemVer，实测 hosts 与 Cargo 双双拒绝。
4. **为什么是严格 SemVer**：宿主校验清单用 `semver::Version::parse`（`crates/ide-extension/src/manifest.rs:330`），失败即拒绝整包；市场判定更新用 `semver::Version` 比大小（`crates/ide-host/src/plugins/market.rs:56`）；安装目录名直接用版本号字符串（`crates/ide-host/src/plugins/install.rs:191`，字符集 `[0-9A-Za-z.+-]`）。前导零、四段、字母段都过不去。
5. **日期版本天然单调递增**：`2026.12.1 > 2026.11.28 > 2026.11.5`，满足市场「新版本号必须大于旧版本号」的要求，不需要手工维护序号。
6. **与里程碑解耦**：内部迭代的里程碑编号只记在提交信息与 CHANGELOG 正文，不进对外版本号。

## 内测版本号（`-beta.N`，规则保留未启用）

原版仓用 `-beta.N` 解决「内测期一天发多轮」的序号问题，对应的是它自己的 Gitee 抢先体验通道与 `update/update.json`。

**本仓没有自更新通道**（版本更新只走市场推送），这个后缀目前没有承载物，因此规则保留、不启用：脚本与 CI 都不做 beta 特殊分支，规范先写在案，将来真有内测需求时按此执行。

| 通道 | 格式 | 示例 |
| --- | --- | --- |
| 内测（同日多版） | `YYYY.M.D-beta.N` | `2026.11.28-beta.1` → `beta.2` |
| 正式（市场） | `YYYY.M.D` | `2026.11.28` |

启用须知：

- 上架市场的版本**必须去掉后缀**。
- semver 语义下同一基号的预发布**小于**正式版（`2026.11.28-beta.1 < 2026.11.28`），所以装了正式版的用户不会被内测清单倒灌，这条在本仓的 `semver` crate 上实测成立。
- 数字后缀按数值排序：`beta.10 > beta.9`。

## 发行标签（git tag）

- **标签名 = `plugin.toml` 的完整版本号字符串，一字不差，不带 `v` 前缀。**
- 必须一致的原因：`docs/registry/` 里的 `package` 字段按标签段拼下载地址（`releases/download/{版本号}/{id}-{版本号}.oiplugin`），标签差一个字符，用户点下载就是 404。`release.yml` 有一条硬断言守着这件事（tag 与清单不符即红）。
- 创建时机：发行提交之后 `git tag 2026.11.28` → `git push origin 2026.11.28`；`release.yml` 由数字开头的 tag 触发。
- 历史 tag `v0.1.0` 保持原样不动：已发布的下载地址依赖它，改历史 tag 会让已下载用户校验失败。

## 版本比较机制

比较逻辑委托 `semver` crate，与宿主判定「有没有新版」用的是同一套规则——不存在「插件端认为有新版、IDE 端认为没新版」的口径分叉。

实测行为：

| A | B | 结果 | 场景 |
| --- | --- | --- | --- |
| `2026.11.5` | `2026.11.28` | A < B | 隔日发版，正常提示升级 |
| `2026.11.28-beta.1` | `2026.11.28-beta.2` | A < B | 同日内测第二轮 |
| `2026.11.28-beta.9` | `2026.11.28-beta.10` | A < B | 数字后缀按数值排 |
| `2026.11.28-beta.1` | `2026.11.28` | A < B | 内测版小于正式版，不倒灌 |
| `2026.11.29-beta.1` | `2026.11.28` | A > B | 次日内测版大于前一日正式版 |
| `2026.11.28` | `2026.11.28` | 相等 | 不提示 |

## 发版流程里版本号相关的动作

1. 改 `plugin.toml` 的 `version` 为当天日期 → 同步 `Cargo.toml` 的 `version`。
2. 同步 `settings/about.json` 与 `src/settings.rs` 里 `about.buildNumber` 的版本号前缀（两处必须一致，`cargo test settings::` 有守卫）。
3. `plugin.toml` 的 `change-notes` 每条前缀改成新版本号（一条一行，一版 ≤8 条）。
4. `CHANGELOG.md` 的 `[Unreleased]` 改名成 `## [2026.11.28]`（段名取版本号原文，`release.yml` 按这个格式提取发行说明）。
5. `bash scripts/check-version-format.sh` 本地过一遍 → 提交走 CI → 打不带 `v` 的 tag。

`engine/ENGINE_VERSION` 与上述无关：那是引擎 jar 自己的版本，归 IntelliJ 仓维护，两边节奏本就不同。
