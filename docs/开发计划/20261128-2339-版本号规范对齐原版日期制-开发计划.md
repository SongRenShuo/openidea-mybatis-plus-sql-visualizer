# 版本号规范对齐原版日期制

> 立项时间：2026-11-28 23:39。触发问题：「这个 openidea 的插件版本号机制和 idea 的一样吗，能不能和原版 idea 的版本号规则一致？」
> 结论：**机制同源、规则可以完全统一**。本仓从 `0.1.0` 切到原版 IntelliJ 仓的 `YYYY.M.D` 日期制，并同步把 git tag 改成不带 `v` 前缀的完整版本号。
> 规范正本落在 `docs/规范/版本号规范-说明文档.md`（移植原版同名文档，按本仓事实裁剪）。

## 1 两边机制核对（先证伪，再定方案）

### 1.1 同为严格 SemVer 三段数字，边界逐条一致

| 版本号形态 | `openidea-plugin check`（0.1.55） | Cargo（`Cargo.toml`） | 原版 IntelliJ 规范 |
| --- | --- | --- | --- |
| `2026.11.28` | ok | ok | 基准格式 |
| `2026.08.13`（前导零） | 拒：`` `version` must be a semantic version like 1.2.3 `` | 拒 | 禁止 |
| `2026.11.28.1`（四段） | 拒：同上 | 拒 | 禁止（上架被拒） |
| `2026.11.28-beta.1` | ok | ok | 仅内测通道 |

实测方式与读数：临时目录写最小 `plugin.toml` 跑 `openidea-plugin check .`；Cargo 侧写最小 `Cargo.toml` 跑 `cargo metadata --no-deps`。四个形态一进一拒，两边判定完全相同。**不是「大致一致」，而是同一条 semver 规则在两边各有一处实现。**

### 1.2 同源的三处实现

| 环节 | 位置 | 事实 |
| --- | --- | --- |
| 清单校验 | `crates/ide-extension/src/manifest.rs:330` | `semver::Version::parse(&self.version)` 失败即报 `` `version` must be a semantic version like 1.2.3 ``，整包拒绝 |
| 市场更新判定 | `crates/ide-host/src/plugins/market.rs:56` | `Version::parse(offered) > Version::parse(installed)`，两端解析失败即 `false`（不提示更新） |
| 安装目录名 | `crates/ide-host/src/plugins/install.rs:191` | 版本号直接当目录名，字符集限定 `[0-9A-Za-z.+-]`、长度 ≤64、不以 `.` 开头 |

原版那边委托 `com.intellij.util.text.VersionComparatorUtil`（见原版仓 `docs/发行说明/版本号规范-说明文档.md`「版本比较机制」节）。**两边的比较语义实测一致**：同一基号下 `-beta.N` 小于正式版，`2026.12.1` 大于 `2026.11.28`，日期版本自然单调递增。原版文档那张 `beta` 边界表在 OpenIDEA 侧同样成立，可直接照搬。

### 1.3 已核实的迁移安全性

- Cargo 接受 `2026.11.28` 形态（`cargo metadata` 实测），`env!("CARGO_PKG_VERSION")` 会原样变成 `2026.11.28`，`about` 行与 `build-info` 输出随之改变，无需改代码。
- `Cargo.lock` 里自身条目（`name = "openidea-plugin-mybatis-plus-sql-visualizer"` / `version = "0.1.0"`）由 cargo 自动重写，**不手改**。
- semver 语义下 `2026.11.28 > 0.1.0`，已装 `0.1.0` 的用户会收到升级提示，不会因为「版本号变小」被市场忽略。这条实测过（`semver` crate 实跑）。
- 宿主按版本号建目录，旧版 `0.1.0/` 目录保留，`previous` 指针机制不受影响，回滚路径不变。

## 3 目标规则（本仓生效）

1. **版本号位置**：`plugin.toml` 顶部的 `version`（`.oiplugin` 的权威来源），`Cargo.toml` 的 `package.version` 必须与之逐字一致。
2. **格式**：`{年}.{月}.{日}`，月与日不补前导零。示例 `2026.11.28`、`2026.12.1`、`2027.1.9`。
3. **一日一版**：同日需再发（热修）并入次日，禁止同日递增后缀（`2026.11.28.1` 四段非法，实测两边都拒）。
4. **git tag = 完整版本号，一字不差，不带 `v` 前缀**。标签差一个字符，`package` 里的下载地址就 404。
5. **内测后缀 `-beta.N`**：规则保留、当前不启用（本仓无自更新通道，后缀没有承载物）。规范文档写清用法与语义，脚本与 CI 不做 beta 特殊分支。
6. **CHANGELOG 段名**：发布当天把 `[Unreleased]` 改成 `## [2026.11.28]`（段名取版本号原文，与 `release.yml` 的 `awk` 取值逻辑一致）。

## 5 不做什么

- ~~不改已发布的 `v0.1.0` tag~~ **2026-11-29 用户决定彻底清除**：`v0.1.0` 是切换前的试验版，tag（本地 + GitHub + Gitee）、GitHub Release 及其附件、登记草稿里的 `0.1.0` 条目一并删除。此后**已发布**的 tag 不再删除或移动。
- **不改 `market/official-pr/` 的既成材料**：见 D4。
- **不做 `-beta.N` 的 CI 分支**：本仓无自更新通道，规则写进文档备用即可。
- **不把引擎版本号绑到本仓版本号**：`engine/ENGINE_VERSION` 归 IntelliJ 仓管，两边节奏本就不同。
- **不引入版本号自动 bump 脚本**：一日一版靠人填日期，比脚本猜日期更准；E1 的门禁已经覆盖填错的形态。

## 7 回退方案

任一前提被推翻时：

- **P1 不成立**（pack 拒日期版本）：版本号退回 `0.x.y` 三段语义化，规范文档改成「本仓用 `0.x.y`，与原版日期制是不同选择」并说明理由；tag 形态切换（阶段 C）仍可独立进行。
- **P2 不成立**（市场拒混列）：登记索引拆两条 publisher 记录或等旧版用户升级完再切换；期间本仓版本号保持 `0.1.x`。
- **P3/P4 不成立**（tag glob 或 gh 拒绝）：tag 保留 `v` 前缀，只切换数字部分为日期制（`v2026.11.28`），并在规范文档登记这条偏离原版的原因。

回退时同步改规范文档与 E1 门禁的正则，**不留「文档说 A、门禁查 B」的分叉**。
