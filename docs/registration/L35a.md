# L35a 注册申请：SQL 预览入口（命令 / 快捷键 / gutter 按钮）

本车道补「SQL 预览」的**入口与宿主侧**：`preview-sql` 命令、mapper 语句行的
gutter 预览按钮、以及两者共用的预览页签落点。UI 版式不在本车道。

原版（IntelliJ 仓）的入口是三个：mapper gutter 预览图标、右键菜单、
`Alt+Shift+Q`（`plugin.xml:68/84`、`:608`）。原版点击后弹 `SqlPreviewDialog`
模态框；OpenIDEA 没有插件可用的模态对话框 API，因此本端口**统一落到侧栏
`sqlv-logs` 工具窗的第 5 个页签**（`sqlv-logs#preview`），渲染链与原版一致，
差别只有外壳。

`plugin.toml` 由主控独占，本车道未改；以下片段由主控在 `chore: 注册汇总` 时一次性应用。

## 1 `plugin.toml` — 新命令

放在现有 `[[contributes.commands]]` 区块内（`open-workbench` 之后即可）：

```toml
[[contributes.commands]]
id = "preview-sql"
title = "MyBatis SQL: Preview SQL"
category = "MyBatis SQL Visualizer"
```

## 2 `plugin.toml` — 新快捷键

`Alt+Shift+Q` 与原版一致。SDK 字段为 `command` / `key`（可选 `mac`）：

```toml
[[contributes.keymaps]]
command = "preview-sql"
key = "Alt+Shift+Q"
```

> 原版该快捷键打开的是 SQL 日志工具窗里的**独立预览页签**并用剪贴板里「像 SQL
> 的文本」预填；本端口的无参形式读**当前编辑器**（选区优先，否则整篇），不读剪贴板
> ——见 §6 差异表。

## 3 `plugin.toml` — 新 provider kind

`gutter-actions` 需要 API 1.4+（本仓 `engines.openidea = "^1.15"`，满足）。
语言只声明 `xml`；非 mapper 文档由代码再筛一次。

```toml
# Mapper 语句行的预览按钮；点击运行 preview-sql（L35a）。
[[contributes.providers]]
kinds = ["gutter-actions"]
languages = ["xml"]
```

## 4 `plugin.toml` — 图标声明

gutter 按钮的 `icon` 返回包内路径 `icons/sqlGutter.svg`（原版同款预览图标）。
gutter 动作的图标只认「图标名 / 别名 / **已声明的** marker SVG 路径」，所以要把
这个既有文件补进 `markerIcons`，安装时才会被打包与校验：

```toml

icon = "icons/sqlGutter.svg"
```

说明：

- 该文件已在仓内（16×16，`circle`/`path`/`line` + `fill`/`stroke`，无脚本/外链），
  能过宿主 SVG 清洗；没有单独的 dark 变体（`iconDark` 可省）。
- **若主控不想新增 markerIcon**：把 `src/providers/gutter.rs` 的
  `pub const ICON` 改成 `"icons/marker-statement.svg"`（已声明，`id = "statement"`）

## 5 `plugin.toml` — 能力

`editor.read` 加到 **optional**（与 `clipboard` / `process:java` / `net:127.0.0.1` 同级）：

## 12 追补（2026-11-28）：Java 侧的预览图标

用户反馈「Wrapper 附近缺少预览图标，相关能力没有对齐原版插件」。根因是 §3 的
provider 只声明了 `languages = ["xml"]`：宿主按 `doc.language` 选 provider，Java
文件从来不会被调用，所以原版那三处 Java 侧入口一个都不存在。

原版的面貌（`WrapperAnchorDetector.kt` + 三个 provider）：

| 原版入口 | 锚点 | 本仓对应 |
| --- | --- | --- |
| `SqlGutterLineMarkerProvider` | Wrapper 链根：变量声明的名字、`new …Wrapper` 的 `new`、`Wrappers.<T>lambdaQuery()` 的方法名 | `wrapper_chain_starts`（文本级） |
| `AnnotationSqlGutterLineMarkerProvider` | 注解的 `@` token（`@Select/@Insert/@Update/@Delete`） | `annotation_statements` 的 `annotation_start` |
| `JdbcTemplateSqlGutterLineMarkerProvider` / `StringSqlMethodGutterLineMarkerProvider` | 字符串实参、方法名本身像 SQL 的调用 | 未做（见 §13） |

### 12.1 声明

```toml
[[contributes.providers]]
kinds = ["gutter-actions"]
languages = ["xml", "java"]
```

### 12.2 参数格式

Java 侧传 `<path>@<byteOffset>`，不是行号：命令用「谁的 span 包含这个 offset」
解析，和光标路径同一条规则；行号要重新按 UTF-16 列换算，且文件在图标与点击之间
改动就会指错地方。`@<offset>` 与既有的 `@<path>` 前缀靠「最后一个 `@` 之后全是
数字」区分。

### 12.3 锚点规则（去重的三档）

1. **一条链只出一枚图标**：`wrapper.eq(...)` / `wrapper.orderByDesc(...)` 这类续写
   语句不产生图标——链根已经代表它们。原版在 `WrapperAnchorDetector` 里做同样的
   让位（`isInsideWrapperVariableInitializer`）。
2. **注解方法体内的链让位**：注解图标已经打开该方法，链根再出一枚就是同一语句两枚
   图标（原版的 `T-MapperPreviewDedup` 同款理由）。
3. **抽象/接口方法的 Wrapper 参数不是链根**：`@Param("ew") Wrapper<T> ew` 是
   `${ew.customSqlSegment}` 的占位符，既无构造也无调用。

### 12.4 设置

`ui.gutter.wrapperChain` 与 `ui.gutter.annotation` 两条从「仅存储」改为已接线；
`ui.gutter.mapperXml` 同样接上（此前 XML 图标无开关）。三组各自独立，关一组不影响
其他两组——`providers_gutter_java_boolean_setting_off_removes_the_group` 钉住这点。

### 12.5 顺带修的抽链缺陷

原 `wrapper_chain_at` 在光标落在链根（声明行）时只返回声明本身，落在续写语句时才
带上续写——同一条链的两个入口得到不同 SQL。现在链根也会把其后的续写语句全部带上，
两者结果一致（`both_icons_of_one_chain_reach_the_same_text`）。

## 13 仍未做的 Java 侧入口

原版另有四类 Java 源码入口，本仓本轮不接：

| 原版入口 | 为什么不做 |
| --- | --- |
| JdbcTemplate / NamedParameterJdbcTemplate 字符串 SQL | 需要识别 receiver 家族（`JdbcTemplate` 变量、`new JdbcTemplate(...)`），无 PSI 只能按变量名与类型文本猜；误亮比不亮更糟 |
| 方法名字符串 SQL（`StringSqlMethodGutterLineMarkerProvider`） | 同上，靠方法名启发，误报面大 |

| iBatis / 通用 XML 内嵌 SQL | 前者只有 `<sqlMap>` 文档级入口，后者同样要按标签名猜，未做 |

## 14 MPJ 联表的处理口径（2026-11-28）

用户贴出的实机结果：

```
SELECT * FROM car_device_info WHERE id = 1
-- [wrapper.render.note] `.lambda` is not rendered by this version
-- [wrapper.render.note] `.selectAll` is not rendered by this version
-- [wrapper.render.note] `.leftJoin` is not rendered by this version
```

三处 `selectAll`/`leftJoin` 被丢弃，SQL 却照常给出。这是**正确性缺陷**而不是能力
缺口：那条语句和原查询的行形状、列清单都不同，读的人会当成事实。

### 14.1 分档（已修）

渲染器现在把「不支持」分两档：

| 方法类别 | 例子 | 结果 |
| --- | --- | --- |
| 决定行形状 / 列清单 | `selectAll` `selectAs` `select*` `selectCollection` `selectAssociation` `leftJoin` `innerJoin` `rightJoin` | `unresolved`，**不出 SQL**，原因 `wrapper.structural_method` |
| 只是少一个过滤条件 | `apply` `exists` `notExists` `having` | `partial`，照常出 SQL |

判据是「丢掉它之后，`SELECT * FROM 主表` 还答是不是同一个问题」：`apply` 是同一个
问题少一个条件；`leftJoin` 换了一组行。前者可以说「部分」，后者只能说「不知道」。

`wrapper.unsupported_method` 保留给第二档，文案不变；新键
`wrapper.structural_method` 说明该链用本版不渲染的方法构造联表或查询列。

### 14.2 为什么不直接补联表

原版 `MpjLambdaConverter` 的 join 支持覆盖：三参 `(Class, 关联表字段, 主表字段)`、
四参带别名、`on(col1, col2)`、lambda ON、5 参别名 + lambda、子表 MConsumer 子查询、
`selectCollection` 前缀形态、`from(子查询)`、`union`、`fill`…… 每一种都要副表
自己的 `TableInfo`（列展开 + 逻辑删除列）与别名映射，实测口径在 MPJ 官方输出上对拍。

本仓无 PSI：副表的表名要从实体类文件里读（`EntityModel`），列要按 `@TableField`
映射，别名默认值是「实体类名首字母小写」，而 `selectCollection` 的 ON 还要复用同子表
`leftJoin` 的条件。这一层可以做，但必须按上表逐形态实现并逐形态对拍——**半套 join
比没有 join 更危险**，因为它会在某些形态上给出看似完整的错 SQL。

所以本轮先止损（不给错 SQL），联表留作独立任务；在它落地前，联表语句请用日志/历史
里的真实 SQL（`sqlv_render_logs` / `sqlv_history_search`），或直接粘到预览输入框。

## 15 MPJ 联表渲染（2026-11-28 实现）

§14 的止损落地后，用户明确要求实现联表，并指出形态清单在**原插件仓库**与
**原插件 demo 仓库**（`mybatis-plus-join-demo`）里都有。实现以两者为规格：

### 15.1 语义来源（逐条对拍）

| 语义 | 出处 |
| --- | --- |
| ON 两侧列**按列自己的实体类**定表别名（不是一律主表） | 原版 A47 修复（`MpjJoinOnAliasConverterTest`）：`rightJoin(AreaDO.class, AreaDO::getId, AddressDO::getAreaId)` → `ON areaDO.id = addressDO.area_id`，`t.area_id` 是真库报错的旧缺陷 |
| 关联表别名默认 = 实体类名**整体**首字母小写（`AddressDO` → `addressDO`） | `MpjLambdaConverter`：`className.replaceFirstChar(lowercase)` |
| 主表别名默认 `t`，`setAlias("x")` 覆盖 | `MAIN_ALIAS_DEFAULT` |
| SELECT 未显式指定时展开主表全部列（带别名前缀），不是 `*` | `SqlGenerator.generateSelect`：`allColumnNames.map { ColumnRef(tableAlias…) }` |
| `selectAll(Class)` 展开该实体全部列；`selectIgnore("col")` 剔除 | `parseSelectAll` |
| 三参 join `(Class, 关联列, 主列)` → `ON 别名.关联列 = 主别名.主列` | `MpjLambdaConverter` 分派 1 |
| 四参别名 / 五参右别名（右别名作用于右列所在表） | demo `joinRightAlias` 注释 + converter 分派 |
| lambda ON / `ext` 追加 ON 条件 | converter 分派 lambda 形态 |
| 子查询条件 `in(col, Class, lambda)` / `exists(Class, lambda)` 不继承主表别名 | `QueryWrapperParser` 子查询注释 |
| 联表 UPDATE/DELETE（`JoinWrappers.update/delete`） | 本轮不做 → `unresolved`（SET 列表与多表删除目标是结构） |

### 15.2 实现形态

- 多实体投影：`EntityColumns.related`（命令层按链内 `X.class` 逐个
  `resolve_class_path` + `parse_entity` 填充；读不到的类不入列，渲染器
  `unresolved` 并指名，不猜表名）。
- 列引用统一按「列自己的实体类」解析为 `别名.列`：条件、ON、ORDER BY、GROUP BY、
  SELECT 全一致（A47 语义）。
- 限定列渲染拆段引用：`t.order` 不能整段 quote（那会变成 `` `t.order` ``）。
- 参数顺序：HAVING 片段的参数排在条件之后；子查询内部含运行期参数时整条链
  `unresolved`（`?` 要插进主语句参数序列中间，文本层排不准，宁可不给）。

### 15.3 本轮覆盖 / 仍不做

覆盖：三参 join、四参别名、五参右别名、lambda ON、`ext` 追加、raw join 片段、
`selectAll()`/`selectAll(Class)`、`select(col…)`/`select("片段")`、`selectAs`、
聚合族（COUNT/SUM/MAX/MIN/AVG 带 AS）、`selectIgnore`、`groupBy`、`having("…{i}…")`、
`in/notIn/exists/notExists` 子查询、`setAlias`。

仍不做（`wrapper.structural_method`，不出 SQL）：`selectFunc`/`selectSub`/
`selectCollection`/`selectAssociation`/`from(子查询)`/`around`/子表 MConsumer
子查询 join、联表 UPDATE/DELETE。理由同 §14.2：这些形态要子查询渲染或多表写语义，
半套会产出看似完整的错 SQL。

### 15.4 列别名语义的再对齐（2026-11-28，同日二次核对）

首轮实现把「ON 侧按列自己的实体类」误推广到了**条件列**与 **`selectAll(Class)`**。
逐条核对原版后修正：

| 列的位置 | 原版规则 | 依据 |
| --- | --- | --- |
| ON（含 lambda ON、ext） | 按列自己的实体类查别名表，无则回落 | A47（`onColumnAlias`） |
| 条件 / ORDER BY / GROUP BY | **一律主表别名**，不管接收者是哪个实体 | `QueryWrapperParser.columnPrefix` 文档：「MPJ 联表场景传主表别名 t」 |
| SELECT 列（select/selectAs） | 按列自己的实体类查 `classToAlias`，查不到回落主表 | `parseSelectAs` |
| `selectAll(Class)` | **永远展开主表全部列**，Class 参数被忽略；第二参字符串为列名前缀 | `parseSelectAll` 用 `table.allColumnNames` + `mainAlias` |
| `join(关键字, …)` 自定义关键字 | 原样透传 | 本轮未做 → `structural`（丢 JOIN 的 partial 出 SQL 比拒绝更糟） |

钉住的用例：`condition_columns_take_the_main_alias_even_for_joined_entities`
（`eq(AddressDO::getStatus, 1)` → `t.status`，与 ON 的 `addressDO.user_id = t.id`
并存）、`select_all_expands_the_main_table_regardless_of_the_class_argument`、
`a_custom_keyword_join_is_structural_not_partial`。

### 15.5 子表 MConsumer 子查询 join（2026-11-28 同日三次）

原版形态：`leftJoin(C, t -> t.setAlias("tt").selectAll().ge(…), left, right)` 把关联表
渲染成子查询。语义取自 `MpjLambdaConverter` 的 `args.size == 4 && args[1] is NestedArg`
分支：

```
LEFT JOIN (SELECT tt.c1, tt.c2, … FROM <子表> tt WHERE …) tt ON tt.<left> = <主别名>.<right>
```

- 子别名：lambda 内 `setAlias("tt")`；未指定则子实体类名首字母小写。
- 子查询自身是 MPJ 语句（`render_with_alias` 带子别名重入）：列带 `tt.` 前缀、
  `FROM <子表> tt`、条件也用 `tt.`——三者同名才能在真库执行。
- ON 左列取**子别名**（`tt.left`），右列按 A47 取列自己的实体别名。
- `selectAll`/`ge` 等子链条件照常走分档规则：含运行期参数时子查询降级为
  `partial`，主链随之 `partial`（不再整体拒绝）。

### 15.6 联表 UPDATE 与 DELETE（2026-11-28 同日四次）

原版语义取自 `UpdateJoinConverter` / `DeleteJoinConverter` 及其测试
（`UpdateJoinDeleteJoinConverterTest`）。链根 `JoinWrappers.update(C)` /
`JoinWrappers.delete(C)`，渲染整条语句：

```
UPDATE `user` t
INNER JOIN user_address addressDO ON addressDO.user_id = t.id
SET t.name = ?, t.tel = '13800000000', t.age = t.age + 1, t.name = concat(t.name, '_u')
WHERE t.status = 1

DELETE t, addressDO FROM `user` t
LEFT JOIN user_address addressDO ON addressDO.user_id = t.id
WHERE t.id = 1001
```

- SET 全族按调用顺序：`set`/`setIfExists`（布尔条件前缀剥离）、`setSql`/`setApply`
  （`{i}` 绑定替换；`setApply` 的 `%s` 槽取 accept-lambda 的列，demo 口径）、
  `setIncrBy`/`setDecrBy`（`col = col ± n`）、`setUpdateEntity`/`setUpdateEntityAndNull`
  （实体字段运行期不可知 → 主表非主键全列 `t.col = ?` 占位近似，两形态同形；
  `@TableId` 列排除——`EntityColumns.primary_key`）。
- 方法引用 SET 列一律主表别名近似（跨表归属静态不可判，原版 KDoc 标注的简化）；
  字符串列自带 `t1.tel` 限定时原样透传。
- 三参 `set(col, otherColumn, value)` 值取自另一列，原版解析失败剔除 SET 清单
  （unparsedSets 警示口径）→ 本版剔除并 `partial`；全部 SET 失败 → `unresolved`。
- 删除目标：`delete(Class)`（主表类 → 主别名，关联表类 → 类名首字母小写，
  **不看** join 显式别名——原版实现如此）、`delete(String)` 原样、`deleteAll()`
  → 主别名 + 全部 join 别名、无 delete → 默认主别名；重复去重保序。
- 条件列照 MPJ 分位（一律主别名，字符串列透传）；`last` 尾缀原样追加。
- `@TableLogic` 逻辑删除改写（全逻辑删除表自动转 UPDATE SET del=1）不在范围，
  语句仍按 DELETE 渲染——原版文档化边界。

### 15.7 子查询运行期参数就地嵌入（2026-11-28 同日四次）

上一轮 `in`/`exists` lambda 子查询含运行期参数时整链 `unresolved`（「参数顺序
文本层排不准」）。本轮证伪该前提：条件树的遍历顺序就是 SQL 里 `?` 的出现顺序，
子查询渲染时把自身参数来源随 `Value::SubQuery(sql, params)` 携带，主语句参数
序列按树序收集即可对位：

```
WHERE t.id IN (SELECT user_id FROM user_address WHERE status = ?) AND t.sex = 1
```

- 子渲染仅参数缺口（`? + 来源`）时接受嵌入；有丢条件、缺投影等其它缺口仍拒绝
  ——半盲子查询嵌进去会读成完整查询，违反「不猜」红线。
