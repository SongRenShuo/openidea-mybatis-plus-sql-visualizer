# 捕获"连上了但没数据"：宿主 WS 是二进制通道，agent 只说文本帧

- 日期：2026-11-27
- 现象：面板点「开始捕获」，Output 打出 `-- capture-start: connected ws://127.0.0.1:17890/mpsv (socket 3, websocket-ready: already subscribed)`，看着一切正常；随后 JVM 控制台出现
  `[T-AgentConfigChannel] WS 会话建立后 15000ms 内未收到任何 CONFIG，按保守策略主动停采（fail-open 看门狗…）`，
  面板一条数据也没有。
- 影响面：`java.agent` 捕获这条链路**完全不可用**，但插件侧所有测试全绿、`openidea-plugin check` 也绿。

## 根因：两端对帧 opcode 的约定相反，且都是静默丢弃

两个仓各写了一半，谁都没错，只是没人把它们连起来跑过。

**宿主（OpenIDEA）只走二进制帧。** `crates/ide-host/src/plugins/websocket.rs`：

```rust
// 出站：插件给的字节一律封成 Binary
if writer.send(Message::Binary(bytes.into())).await.is_err() { ... }
// 入站：只把 Binary 交给插件，Text 落到 `_ => {}` 被丢掉
Some(Ok(Message::Binary(bytes))) => { connection.incoming.push(bytes.to_vec()); ... }
Some(Ok(Message::Ping(bytes))) => ...,
Some(Ok(Message::Close(_))) | Some(Err(_)) | None => break,
_ => {}
```

`io.wit` 的 `resource websocket { send: func(bytes: list<u8>) }` 只收字节、不区分文本/二进制，所以
"发出去的是 Binary" 是宿主实现选择，插件侧无法影响。v0.1.51 / 0.1.52 / 0.1.53 / main 四个 checkout
的这段代码逐字相同，不是某个版本的回归。

**agent 只认文本帧。** `WsSenderLoop.runSession` 原先只处理 `OP_TEXT` 与 `OP_CONTINUATION`，
`OP_BINARY` 走"其他 opcode（binary 等）不属于本协议：忽略但不中断"；出站 `writeEnvelope` 固定
`WsFrameCodec.OP_TEXT`。它自己就是 RFC 6455 服务端（手写握手 + 手写拆帧），不是通用 WS 库。

于是两个方向互相丢帧：

| 方向 | 发送方 | 帧类型 | 接收方 | 结果 |
| --- | --- | --- | --- | --- |
| 插件 → agent（CONFIG） | 宿主 | Binary | agent | 忽略，`configSeen` 永远 false |
| agent → 插件（HELLO/心跳/事件） | agent | Text | 宿主 | 丢弃，插件收不到任何帧 |

唯一的可见症状就是 15 秒后那条看门狗——因为它是 agent 唯一会打印的东西。**两端都不报错**，这正是
最难查的一类：日志里没有一条"解析失败"，只有"没收到"。

## 修法：agent 侧让 opcode 跟随对端

改在 agent（`sub-projects/sql-visualizer-agent`，本仓 L7 所有权），因为插件侧改不了宿主的封帧方式：

1. **入站**：`OP_TEXT`、`OP_BINARY`、`OP_CONTINUATION` 同等对待——载荷是同一份 UTF-8 JSON 信封，
   opcode 只说明对端是谁。收到 `OP_BINARY` 就把出站 opcode 切成 `OP_BINARY`。
2. **出站**：`writeEnvelope` 多一个 opcode 参数，全部调用点传当前值。默认仍是 `OP_TEXT`，
   所以 **IntelliJ 插件的 WS 客户端行为逐字节不变**（它发文本、收文本）。
3. 用 `final int[] outboundOpcode` 而不是可变局部变量：`EventBus.drainOverflow(agg -> writeEnvelope(...))`
   的 lambda 要捕获它，局部变量不能既变又被捕获（同文件里 `slot` 数组已是这个写法）。

为什么不是"干脆永远发 BINARY"：IntelliJ 侧的通用 WS 客户端按文本回调收帧，突然收到二进制会走另一条
回调分支，等于把另一个产品弄坏。镜像对端是唯一同时满足两边的解。

时序上没有竞态：agent 连上后立刻写的 HELLO / 补发心跳仍是文本，会被宿主丢掉；但插件 `connect()`
在返回前就下发 CONFIG，agent 读到它即刻切到二进制，之后的心跳与事件都能到达。丢一条 HELLO 无影响
——插件只把它当控制帧记录，不参与任何判定。

## 验证

- 新增 `WsSenderLoopEndToEndTest.二进制客户端_入站CONFIG生效且出站镜像BINARY`：真 socket、真握手，
  扮演宿主——入站用**掩码 BINARY** 帧下发 CONFIG，断言拿得到 `CONFIG_ACK`，且后续事件也以
  `OP_BINARY` 到达。
- **反向验证**：把 agent 的生产代码 `git checkout` 回未修复版（测试保留），该用例
  `java.net.SocketTimeoutException: Read timed out`——一个字节都收不到，正是线上形态；恢复修复版后
  `tests="2" failures="0"`。
- 产物层核对：新 jar 与旧 jar 的 `WsSenderLoop.class` 用 `javap -p` 对比，
  `writeEnvelope` 从 `(OutputStream,int,String)` 变成 `(OutputStream,int,int,String)`；
  装进 `.oiplugin` 后包内 jar 与工作树 sha256 相同（`9e609893…`）。

## 可复用的判断

- **"连上了但没数据"先怀疑帧类型/协议层，不要先怀疑业务逻辑。** 两边都不报错、只丢帧时，日志里
  只有"没收到"，不会有"解析失败"。
- **跨仓的两半协议必须有一条真 socket 的端到端用例，且用例要扮演真实对端。** 原来的 e2e 用例扮演的
  是 IntelliJ 形态的客户端（文本帧），所以它在宿主形态下照样绿——**用例替谁说话，就只验谁**。
- 平台把 `send(bytes)` 当二进制是一种设计选择，不是 bug；插件侧无法改变，只能让对端迁就。
